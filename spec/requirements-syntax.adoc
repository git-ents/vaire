# Requirements Syntax

vaire requirement records in AsciiDoc.
Written after the MVP; reflects what `crates/vaire` accepts.

== 1. Scope

.Conforming document
* Parses under stock Asciidoctor and acdc with no extension loaded.
* Degrades to an anchored open block with attributes (no extension loaded).
* Passes `vaire check` with zero violations.

.Conforming processor
* Extracts requirement records without reserializing non-requirement content.
* Preserves byte identity on extract-then-emit of an unmodified record set.

== 2. Block form

* A requirement is a delimited open block (`--`) carrying the style
  `requirement`.
* `====` (example blocks) is not used: an example block cannot contain another
  `====` block one level down, and requirement bodies need examples
  (parenthetical: the seed syntax used `====`; the open block replaced it).
* The `--` open block nests `====`, `[.example]`, and every other block.
* Attribute lines stack above the block, one concern per line.
* Later attribute lines override earlier lines on the same key (AsciiDoc
  Language spec, block attribute line semantics).
* Attribute values containing `,` or `]` need quoting: `rationale="a, b"`.
* acdc (0.9.0) does not recognize an indented open block with indented
  attribute lines; requirements MUST NOT be indented
  (unspecified in the AsciiDoc Language spec; Asciidoctor is more permissive).
* The block span reported by acdc starts at the first attribute line, not at
  the delimiter.
* Extraction resolves block locations as source *lines*, never as acdc byte
  offsets: acdc reports those in preprocessed coordinates, where `\r\n` has
  already become `\n` and trailing whitespace is gone. LF, CRLF, and mixed
  line endings therefore extract identically, and `body_raw` keeps the raw
  bytes between the delimiter lines, terminators included as written. A lone
  `\r` is not a line terminator; a file using only `\r` has no requirement
  lines.
* Unterminated `--` blocks are parse errors naming the file, line, and byte
  offset; no record is fabricated. acdc reads `--` immediately followed by
  `--` as the start of a nested open block, so an empty block is rejected the
  same way (a block holding one blank line is valid).
* A `requirement`-style attribute line above a `====` example block is a
  parse error naming the file and location: extraction fails loudly instead
  of fabricating a record from a block that cannot carry nested examples.
* Indented requirements stay unsupported (acdc cannot parse them): the shape
  "attribute line carrying a requirement style or id anchor, then an
  indented `--`" is reported as a parse error naming the file and location.

== 3. Identity

* The id is the AsciiDoc anchor via the `#` shorthand on the first attribute
  line: `[requirement#SWR-0142]`.
* `<<ID>>` and `xref:file.adoc#ID[]` work with no extension loaded.
* One id per requirement. Ids are immutable through `emit`.

.ID grammar (ABNF)
[,abnf]
----
id            = ALPHA *( ALPHA / DIGIT / "-" / "_" )
requirement   = "[" style "#" id "]" 1*attribute-line open-block
style         = "requirement"
----

* Uniqueness scope: the file set given to `vaire check`.
* Include trees are resolved by their member files; `vaire check` sees one
  flat file set (includes themselves are not followed by the MVP).

== 5. Body structure

* First paragraph of the body: the normative statement.
* Prose carries the modality keyword; validation enforces agreement (V4).
* The keyword match is ASCII case-insensitive (`SHALL` agrees with
  `modality=shall`) and word-bounded: neighboring ASCII alphanumerics
  disqualify a hit, so `marshaled` is not `shall`, while trailing
  punctuation (`shall,`) still counts.
* The keyword may sit on any line of the leading paragraph; the paragraph's
  lines are joined before matching.
* AsciiDoc inline markup is not interpreted: a keyword inside a code span or
  emphasis still counts, so a literal `shall` beside a real one is a
  compound statement (V5).
* One modality keyword per statement (V5).
* Nested blocks follow, with roles:

[cols="1,3"]
|===
|Role |Content

|[.rationale]
|why the requirement exists

|[.acceptance]
|unordered list of acceptance criteria

|[.note]
|clarification, not normative
|===

== 6. Quality requirement form

* `kind=quality` requirements use Planguage as a description list.
* `Scale::`, `Meter::`, `Must::`, `Plan::` entries.
* `Must::` is the normative level; V4 checks for its presence instead of a
  prose keyword.
* `characteristic` names the quality dimension.

== 7. Traceability

* Links point upward only: `refines`, `derives-from`, `satisfies` live on the
  requirement.
* Downward links live in the artifacts that implement or verify.
* Cross-file resolution: trace targets resolve against the ids of the whole
  file set passed to `check`.
* A trace to the requirement's own id resolves (no V2) but does not make the
  requirement a parent: an unverified self-tracing leaf still fails V3.
* Dangling target: error (V2).
* Cyclic trace graphs: forbidden by this spec; the MVP does not detect cycles
  (see open questions).

== 8. Data model

* `extract` emits a JSON array of records; one record per requirement block.

[,json]
----
{
  "file":       "path exactly as passed to extract",
  "id":         "SWR-0142",
  "span":       { "start": 0, "end": 640 },   // attr line 1 .. close delimiter
  "attr_lines": [
    {
      "start": 0, "end": 25,                    // byte span, newline excluded
      "raw":   "[requirement#SWR-0142]",
      "items": [
        { "style": "requirement" },
        { "id": "SWR-0142" }
      ]
    },
    {
      "start": 26, "end": 66,
      "raw":   "[modality=shall, kind=functional]",
      "items": [
        { "kv": { "name": "modality", "value": "shall" } },
        { "kv": { "name": "kind", "value": "functional" } }
      ]
    }
  ],
  "delim": "--",
  "body_raw": "raw body bytes between the delimiters, terminators included as written"
}
----

* `items` is the editable surface: `emit` re-renders only lines whose items
  differ from the current file.
* Merged field view (`fields()`): later lines override earlier lines.
* Raw items (`Item::Raw`) are preserved and re-emitted verbatim.

== 9. Round-trip semantics

[cols="1,3"]
|===
|Class |Content

|Preserved byte-exactly
|titles, prose, includes, attribute entries, comments, whitespace, block
bodies, delimiters, all unedited attribute lines

|Normalized on edit
|the single re-rendered attribute line (`[style#id, k=v, ...]`); quoted
values re-quoted when needed; item spacing inside that line only

|Rejected as unrepresentable
|id renames; attribute line addition/removal; record ids absent from the
target file; body edits via `emit`
|===

== 10. Validation rules

[cols="1,2,1,3"]
|===
|Rule |Condition |Severity |Message shape

|V1
|id appears more than once in the file set
|error
|`V1: <file>: duplicate requirement id [<id>]`

|V2
|trace target id absent from the file set
|error
|`V2: <file>: <key> target `<id>` not found [<id>]`

|V3
|no requirement links upward to this one and `verification` absent
|error
|`V3: <file>: leaf requirement has no verification attribute [<id>]`

|V4
|prose lacks the modality keyword, or `kind=quality` lacks `Must::`
|error
|`V4: <file>: prose does not carry modality `<m>`: "<statement>" [<id>]`

|V5
|more than one modality keyword in the statement
|error
|`V5: <file>: more than one modality keyword in the statement [<id>]`

|V6
|named attribute not in the vocabulary
|error
|`V6: <file>: unknown attribute `<name>` [<id>]`
|===

* All rules are errors; any violation exits nonzero.
* One violation per offending item: each unresolved trace target raises its
  own V2 and each unknown attribute name its own V6; a repeated id raises
  V1 once, on the later occurrence (file-argument order, then source order).

.Checking files (`vaire check`)
* `check` validates exactly the files named on the command line; id
  uniqueness and trace targets resolve against that whole set. Includes are
  not followed: callers pass the member files themselves.
* Violation order is deterministic: file-argument order, then ascending
  span start, then rule code V1–V6; full ties keep source order.
* Locations: each violation carries a raw byte `offset` into the file as
  read and a 1-based `line` counted over `\n` terminators, so LF and CRLF
  files report the same line numbers while CRLF offsets sit ahead of their
  LF equivalents by the `\r` bytes before them.
* Output:
** Default: one violation line per violation, on stderr.
** `-q`/`--quiet`: no violation lines; the exit code is the only signal.
** `--summary`: two lines on stdout — totals (`checked N files, N
   requirements, N violations`) and per-rule counts (`violations by rule:
   V1=0 ... V6=0`) in fixed rule order. Violations stay on stderr; with
   `-q` only the summary prints. The summary always counts every violation,
   whatever `--rule` displays.
** `--format json` / `--format compact`: one report object on stdout, never
   colored: `file_count`, `requirement_count`, `violation_count` (every
   violation, whatever `--rule` displays), and `violations` — each with
   `rule`, `file`, `id`, `message`, `line`, and `offset`. `--quiet` leaves
   the report untouched. Conflicts with `--summary`.
** `--rule V1..V6` (repeatable): limits the violations displayed — human
   lines and the JSON `violations` array — to the named rules. The exit
   code, `--summary`, and `violation_count` always reflect every violation.

== 12. Examples

.Valid: the seed requirement (passes; `tests/corpus/seed.adoc`)
[,asciidoc]
----
[requirement#SWR-0142]
[modality=shall, kind=functional, status=approved]
[source=STK-014, verification=test, volatility=low]
[refines=SYR-0031, allocated-to=arm.control]
--
The joint controller shall publish a `JointState` sample within 2 ms of
each encoder read.

.Rationale
[.rationale]
Impedance control diverges above 2 ms of feedback age.

.Acceptance
[.acceptance]
* p99 publish latency <= 2 ms over 10^6 samples at 1 kHz
* zero dropped samples at 3x nominal CPU load
--
----

.Valid: quality requirement (passes; `tests/corpus/seed.adoc`)
[,asciidoc]
----
[requirement#SWR-0207]
[kind=quality, characteristic=availability, modality=shall]
[verification=analysis]
--
Scale:: uninterrupted control-loop hours
Meter:: soak test, 72 h, nominal payload
Must:: 500
Plan:: 2000
--
----

.Valid: refined-from-parent (passes; `tests/corpus/traces.adoc`)
[,asciidoc]
----
[requirement#SWR-0005]
[modality=shall, kind=functional, verification=analysis]
--
The controller shall log every fault with a timestamp.
--

[requirement#SWR-0004]
[modality=shall, kind=functional, verification=demonstration]
[refines=SWR-0005]
[rationale="safety interlock must respond before motion", allocated-to=safety]
--
The interlock shall stop motion within 50 ms of a trip signal.
--
----

== 13. Open questions

* Quoting for attribute values containing `"` itself?
* Cycle detection over the trace graph: specified, not yet enforced.
* Is `status` vocabulary closed, or user-extensible?
* `rationale` as attribute vs `.rationale` block: allow both, or one?
* Indented requirements inside list items: contribute span support upstream
  to acdc, or forbid forever?
* Editing body text through `emit`: line-splice bodies, or never?
